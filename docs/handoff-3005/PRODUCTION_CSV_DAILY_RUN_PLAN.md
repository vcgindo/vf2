## 1. Outcome and scope

An operator supplies a completed, dated CSV batch and invokes one checked-in command. That command preserves the supplied files, validates the batch, executes the existing native ingestion/calculation, prepares the complete report roster and downloads, selects the result, restarts only MTA, checks application readiness, and reports a final outcome. Windows Task Scheduler or a Linux scheduler can invoke exactly the same command later.

CSV parsing and operational coordination are the additions. Native calculation, source ownership, approval processing and report semantics remain authoritative. No new calculation engine, copied business rules, SQL Server dependency, legacy BAT/SQLCMD invocation, parity mode or output seed is introduced.

The starting prerequisite is an explicitly initialized application using the existing `initialize_production` operation. First-time master/opening onboarding remains separate from recurring daily execution. This delivery does **not** pretend that an arbitrary initial master CSV can replace the complete native initialization contract: that contract also contains configuration, hierarchy, exclusions and declared opening histories. The current native initialization JSON and its original bytes remain supported. Daily master/supplier CSVs are included where the initialized native policy permits external feeds; active-NMS database-owned masters are not replaced by files. A universal CSV-based first-time onboarding/import wizard is outside these two deliverables.

Target fresh clone/build/install/onboarding for this release and a newly registered isolated test namespace. Native application capabilities seal schema, objects, grants and implementation identity. Merely applying a migration and replacing an image on an already sealed initialized instance is not a valid upgrade procedure. Existing initialized instances, including the current starter and3005, remain untouched. In-place adoption of this new capability requires its own explicitly approved, proven compatibility/upgrade route; do not discover that restriction only after attempting to upgrade them.

A small optional development helper will convert the retained raw starter inputs into the documented CSV batch for testing. It stays outside the production runtime. Building a general synthetic-data factory, customer-specific extraction, API intake, UI upload, automated business actions, holiday/calendar policy, public deployment and capacity benchmarking are excluded.

## 3. Operator interface and deployment configuration

Proposed normal invocation, from the installed clone:

```powershell
pwsh -NoProfile -File ./release/run_daily.ps1 -BusinessDate 2026-10-19
```

The script uses the configured incoming root and the `2026-10-19` subdirectory. `-InputDirectory` may explicitly override that date directory inside the configured allowed root. `-InspectOnly` checks files/configuration/native eligibility without executing a day or changing serving state. `-Resume` reconciles an interrupted job and continues only a safely resumable phase. These are proposed interfaces, not currently available commands.

Use PowerShell 7, already required by the Windows source runbook, for the one host wrapper. It also runs under `pwsh` on Linux. No host Python, Docker socket mounted into a container, Celery beat, daemon, watcher or additional web endpoint is needed. Windows Task Scheduler and cron examples will call this same wrapper with a supplied business date. Neither a schedule nor a business-date/calendar policy is silently installed.

Proposed env keys:

| Key | Purpose |
|---|---|
| `VF_DAILY_INPUT_DIR` | Absolute host root containing completed dated batches; read-only in the daily worker. |
| `VF_DAILY_BINDING_FILE` | Private operator-owned onboarding binding, mounted read-only. Binds initialization UUID, configuration/source digests, recipe/intake policy, original opening file/hash, explicit report/validation policy, separately declared first-day consumer-opening file/hash, and the expected file roster. No secrets or business row payloads in this binding. |
| `VF_DAILY_STATE_DIR` | Host directory for the wrapper's exclusive project lock, final summaries and control logs; outside Git. |
| Existing MTA data/selection/Pick settings | Reused for owned archive, generated native input, downloads and selected-run storage. No second report store. |

The onboarding binding is produced/validated from the existing initialization receipt and its exact original input, plus the explicit native first-day consumer/report contract. It is configured once, not reconstructed manually each day. **Not all daily policy is in initialization today:** the retained initialization's `daily_publication_config` supplies the BPR remark horizon, whereas BOR/RRR history horizons and output-contract selection are supplied in `producer_sources.report_policy`; first-day requests/remarks and report opening are also explicit daily-envelope declarations. Store their approved policy values and file references in this binding, validate them with existing native validators, and never assume they can all be read from the initialization or silently copy sample values into production. The first-day opening may contain only legitimate opening facts/history, never calculated answers; successors must use persisted owners. Deployment settings remain distinct from raw feeds and from authentication scopes. Missing original opening bytes, conflicting initialization/configuration or incomplete file ownership stop before calculation. Do not synthesize them from a report or from a different database.

The dedicated `daily` Compose service uses the same MTA image and runtime DB role, private runtime secrets, read-only root filesystem and a writable MTA data volume. Its input/binding mounts are read-only. It has no host ports, no serving process, no installer/admin secret and no automatic restart. It does not prescribe production CPU/memory/swap ceilings. Existing optional resource-test settings remain opt-in. Normal serving retains its read-only MTA data mount. No temporary selection-writer Compose file is needed from the operator.

## 4. CSV batch contract

The producer writes into a temporary date directory, completes/closes all files, writes `batch.json`, and adds a `READY` marker last (or atomically renames the completed directory into place). A missing marker means “not ready,” not “empty input.” The coordinator snapshots and hashes every listed file before admission; later producer changes cannot change the admitted run. The producer does not have to compute native SHA/revision/predecessor arguments.

`batch.json` contains only a version, batch ID, business date and explicit feed/file availability declarations. Settings such as report policy, validation flags and history horizons come from the validated onboarding binding and its initialized configuration, including explicitly bound native policy not present in initialization itself; daily files do not override them. Header-only CSV means explicitly empty. A missing file is never silently an empty population. Existing allowed missing-feed behavior, such as the native order availability state, must be explicitly declared and passed through its existing preflight; no new default is invented.

| Proposed CSV filename | Native destination / owner | Applicability |
|---|---|---|
| `DailyDataRaw.csv` | `day.raw_daily` | Required. Columns: `SKUCode,WhCode,Stock,Consumption,GIT,Receipts,PSO,ReportDate`. |
| `MasterDataRaw.csv` | `day.raw_master`, schema `Importer/MasterDataRaw` | External-master v2 intake only. Existing metadata defines all81columns; do not publish a shortened invented master schema. |
| `SOBDataRaw.csv`, `MOQDataRaw1.csv`, `MOQDataRaw2.csv` | `day.supplier_feeds` | External-supplier v2 intake only; preserve the native raw1/raw2 ownership/derivation rules and validate permitted populations. |
| `MasterDataRawNonNMS.csv`, `NoNormMasterRaw.csv` | `day.raw_non_nms`, `day.raw_no_norm` | Explicit populations required according to the initialized configuration; non-NMS feed forbidden when disabled. |
| `AcceptedNorms.csv` | `day.accepted_feed` | Only the external feed explicitly supported by the native contract. It does not replace UI Apply/Sleep commands or owned MDM approval queues. |
| `OrderFeed.csv` | `day.order_feed` | `OrderID,SKUCode,WhCode,Qty,CustomerExpDate`; retain the explicit PRESENT/MISSING distinction. |

| `Transporters.csv` | `producer_sources.transporters.rows` | `TransporterCode,TransporterName,TransporterContact`. |
| No daily file | `new_force_requests`, `control_requests`, DB-owned master/task/history/current request/remark state | Use existing capture owners. The adapter supplies only the native empty external queue slots required by that ownership contract; it must reject CSV attempts to supply approved actions or overwrite these owners. |

The contract module will derive column names, widths, precision, NULL rules and types from `STORAGE_TABLES`, the pinned physical schema and the existing producer field declarations. It will expose one generated schema/template report for operators and tests. Do not maintain another independent hand-written copy of all master columns. Distinguish `Importer/DailyDataRaw` physical metadata from the actual native `Intermediate/DailyData` mapping; verify equality where reused instead of assuming table names are interchangeable.

Supported syntax: comma delimiter, standard doubled-quote escaping, UTF-8 with optional initial BOM, LF or CRLF record separators, quoted embedded separators/newlines. Exact declared header roster; reject missing/unknown/duplicate columns and wrong row widths. Emit templates in one documented canonical column order. Preserve data-row occurrence order and duplicates, identifier spelling/leading zeroes, exact decimal values and text whitespace. `\N` is NULL; an empty text field remains empty, while an empty numeric/date field is invalid rather than guessed zero/NULL. A literal text value equal to the reserved NULL token is rejected. Dates/timestamps follow their native field contract; no locale parsing, timezone guess or floating-point decimal round-trip. Existing downstream ASCII/collation/capability limits still apply even though the file itself is UTF-8.

Reject symlinks, paths outside the configured root, traversal, nonregular files, duplicate filenames and files changed while being snapshotted. Do not execute scripts, open ZIP uploads, scan unrelated directories or make incoming files writable. Hash/copy in chunks. Streaming CSV read does not imply that the existing in-memory engine has become a streaming or capacity-qualified engine.

## 5. Complete execution sequence

1. **Inspect and reserve.** The wrapper validates its project, date/path and actual Compose service identities. Acquire a project-scoped exclusive host file handle (`FileShare.None`), then a nonblocking PostgreSQL job advisory lock scoped to initialization. Use the Django connection's configured TLS/session settings; do not copy a helper that drops DB options. A durable unfinished attempt blocks a different day even after the session lock is released. No stale-timeout takeover.
2. **Freeze the batch.** Create a unique owned attempt directory under MTA data. Copy original CSV/control bytes read-only into it, recording file SHA/size and source-record mapping. Never move/delete the producer's originals. Persist the immutable batch identity; a different payload for an already committed date is a conflict, not another revision.
3. **Validate and adapt.** Parse every required population and collect actionable file/record/column errors. Reuse native type and preflight checks. Construct the existing v3 envelope and its configured v1/v2 intake; retain its generated bytes/SHA beside the originals. Derive consumer/report opening only from the declared first-day onboarding binding; a successor supplies `None` and uses persisted own state. Resolve initialization and the unique own immediately preceding SUCCEEDED run, verify full initialization binding, and save its output identity.
4. **Quiesce the MTA API.** After preflight passes, the host wrapper stops only the owned MTA service for the mutation/publication window. Auth, frontend, MTO, PG and Redis stay running. This intentionally bounded maintenance window avoids presenting a stale generation while daily current-state writers execute. Parsing failures do not interrupt the application. A second process/another host cannot enter business execution while the job record is unfinished.
5. **Execute once.** The worker calls `production_daily.execute`/`execute_day` with stable revision, exact generated input hash and verified own predecessor. The existing service captures approved native inputs and performs all ordinary validation/calculation/typed persistence. Bind the feed attempt to its actual `CalculationRun` during the existing durable header transaction. Do not add a second whole-day transaction, producer recomputation or per-script execution framework.
6. **Preserve outcome and diagnostics.** Read actual run status, typed inputs/closing and rejection outcomes. File/schema failures are distinct from canonical business rejections. Some native rules reject a table/subset or carry prior data and still permit processing; preserve those rules instead of imposing “any rejection aborts all.” A successful day with such records is reported explicitly as “published with rejections.” A canonical blocking failure stops with its exact reason.
7. **Prepare one committed generation.** Against that same SUCCEEDED run, reuse the full20-layer preparation coordinator, Planning summary and Guided aggregates. Generate/verify existing Pick/native downloads including InputData.zip. Reuse verified layers after interruption; never calculate the day again to repair publication. For an existing InputData.zip, verify exact original-input/run identities and manifest/content before reusing it; mismatch is a stop, not overwrite.
8. **Validate and select.** Perform existing native admission with full row verification. Save the prior selection bytes and candidate digest. Atomically replace the selection file only after all required preparation/download/admission gates pass. Clear `VF_MTA_SELECTION_FILE`, published run/digest and BTR generation only in the non-serving daily worker so it does not inherit stale serving settings. The real MTA service continues using its configured selection path; no permissive serving flag is added.
9. **Start and prove serving.** Start the same MTA service without build or dependency recreation. Verify container health, selected run/date/digest, MTA `/readyz` and gateway readiness; a merely successful Docker start is insufficient. The existing native guard compares the process-loaded selection with the file, so a stale process cannot count as ready. Confirm the exact expected generation before marking the job PUBLISHED.
10. **Finish.** Write one atomic summary and release the host lock. Exit0 only for verified PUBLISHED or a reverified already-published identical batch. On failure write the phase/error and next permitted action, preserve all inputs/attempts, stop advancement and release held resources in `finally`. An MTA restart is attempted only according to the phase-specific recovery rules below.

The worker emits one final structured summary on stdout and phase logs separately. The wrapper does not parse interleaved output from chained management commands; use Python service functions and explicit receipts. Never print Compose-resolved secrets or whole incoming business datasets to the console.

## 6. Durable state, concurrency and recovery

Add one small `DailyFeedAttempt` metadata model, not a job queue or duplicate business-state store. Fields: BigAutoField internal ID plus unique opaque attempt UUID, initialization FK, business date, caller batch ID, immutable request/batch digest, generated-input SHA, source/configuration digests, predecessor FK/output digest, nullable actual run FK, phase/status, archive path, prior/candidate selection digests, bounded counts/error summary and timestamps. File receipts and row-level rejection records remain append-only owned files; calculation/input rows continue in existing typed relational tables. No JSONB state payloads, passwords or CSV bodies in this model.

Use a unique immutable request key and a partial uniqueness constraint preventing two live/committed/publication-pending jobs for the same initialized date. Historical rejected attempts remain. Under the initialization-scoped lock, also reject a new day while a prior date has unfinished serving/publication. Completed identity is determined from actual `CalculationRun`, capture/publication/selection rows, not solely from this metadata. Add the migration and exact runtime grants through existing installer ownership; runtime has no DDL, role creation or installer secrets.

| Boundary observed on restart | Required behavior |
|---|---|
| Invalid/incomplete batch; no run created | Preserve errors, leave current serving state alone. A corrected completed batch gets a new recorded rejected/accepted attempt identity, not overwritten evidence. |
| Job exists but no committed capture/header | Reconcile actual absence; explicit resume may continue the same frozen request. No initialization or registration replay. |
| Native run RUNNING after interruption | Stop/report; do not assume the writer is dead based on elapsed time. Prove owned process/session termination and reconcile actual rows/capture before using the existing narrowly supported failure/retry operation. |
| Native run FAILED | Preserve rows/capture/error. No automatic retry/reset/new revision. An explicit native retry must reuse its exact eligible frozen capture and pass native retry gates. A new business-rule/data-policy decision is escalated. |
| Run SUCCEEDED; preparation incomplete | Resume publication only against that run/output; reuse validated layers. |
| Selection written; serving check incomplete | Reconcile file/run/candidate identities; resume start/readiness only. Never execute the day again. |
| Same batch/date already PUBLISHED | Verify its run/output/publication/selection and current serving. Return already-published success without business execution. If current selection legitimately advanced, report the historical job as complete without selecting it backward. |
| Different input for consumed date or competing predecessor | Fail with a conflict and exact existing identity. No implicit fork or accepted-day replacement. |

Do not promise that the old app can always be restored merely by replacing its selection file: daily native writers may have advanced mutable current masters/queues. Before any business mutation, its old serving state can be restarted unchanged. After commit, prefer completing the same run's publication. If that is impossible, leave the failed candidate unselected and report the maintenance state. Re-serving the old generation requires existing admission to pass; otherwise recovery requires a matching approved data backup/restore, not file-pointer rollback or silent source repair.

Diagnostics must survive a failed calculation transaction. Add a narrowly scoped production intake error carrying the already-produced rejection table/stage outcome at existing master/supplier/daily abort points; the outer service/coordinator persists it after rollback. Do not add tracing hooks, invoke producers again or turn a failed run into success. Capture decoding/preflight errors directly with their actual codes; never invent a legacy reason code for a new transport error. Retain known row ordinals and say when a rejection relates to the full table or a derived relation instead of inventing a line mapping.

Each attempt directory contains original files, generated native day JSON, manifest/schema identity, `validation-errors.csv`, `business-rejections.csv` when applicable, phase log and final `result.json`. A summary states counts as supporting information, never as substitute proof. Preserve old failed attempts and original bytes; automatic retention/deletion and email alerts are outside this first delivery. Directory/volume permissions protect production inputs and rejection reports from ordinary UI users.

## 8. Cohesive delivery sequence

This is one implementation item with three reviewable engineering milestones. Do not release “CSV parsing complete” as if the user could already run the application, and do not split intake and coordination into separate plans/approval queues.

1. **Working CSV-to-published application path.** Implement contract, parser, attempt/migration, wrapper and native/publication integration together. Produce the operator schema/example bundle. Exit: one command takes a completed batch through real PostgreSQL native execution, all report preparation and a selected, healthy MTA generation on the isolated target. Parser-only or calculation-only success does not close this milestone.
2. **Reliable daily operation and recovery.** Finish the own successor, duplicate/concurrency guards, persistent rejection reporting and phase-specific publication/serving resume on the same flow. Exit: the finite matrix below passes, failed evidence is retained and accepted dates are not recalculated. Existing native rollback/engine parity evidence is reused where unchanged.
3. **Reproducible production handoff.** Verify source export/installer grants and image contents, run the command from documented packaging, complete agreed original UI verification and write the final schema/operations/recovery examples. Exit: clean committed/pushed source, exact image/target/run receipts and manual/scheduled invocation documentation; no automatic schedule, public deployment, cutover or sample loading at installation.

Planning estimate: **16–24 hours of active implementation and affected verification**, assuming no native business-rule defect and an approved isolated target/UI test window. This is an engineering estimate, not a guaranteed runtime or a reason to weaken exits. Report a material new defect as soon as evidenced; do not spend another open-ended investigation tranche or rerun accepted campaigns to consume the estimate.
